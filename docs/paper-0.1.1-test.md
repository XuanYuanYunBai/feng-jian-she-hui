# FeudalSurvey 0.1.1 实服测试记录

2026-11-21，在 Linux 临时实例中通过真实 Paper 控制台运行测试。Paper 26.3 stable build 257，Corretto 25.0.5.1，JVM 可见 4 个处理器，最大堆 2 GiB，视距与模拟距离均为 3。固定种子 `-19799341`，主世界出生方块 `(16, 76, 80)`。全程 0 名玩家，关闭空服自动暂停，仅监听本机。启动日志中出现过 Minecraft Services 公钥获取告警。本轮验证使用控制台。

服务端 JAR 的 SHA-256 为 `64a5bd44910cb982b2648e9a35036cc95a6de4d561e15812aecf5411f84f7b01`。测量所用 0.1.1 插件的 SHA-256 为 `bd7cf482740225a8b0c2e28a3c4fe261483061e66a93b7b8528fc10cb8e63ddd`。

## 复现的故障

0.1.0 在第 7 个区块提交后遭遇进程强退。重开后 SQLite 的汇总与明细一致，但从磁盘解码的区块 `(-1, 3)` 只有 113 块铜矿，账本记了 116。与未强退的同存档副本对照，有三个位置的铜矿变成了石头。

0.1.1 每次按圈内顺序预生成最多 32 个区块，在服务器线程调用 `World.save(true)` 等待存盘，再取得快照并提交计数。Paper 会提示手动保存可能影响运行性能。该流程用于开服前勘测。

## 复验步骤与实测值

在新世界把 `initial-radius` 与 `ring-step` 设为 1，`max-radius` 设为 2，`ticks-between-chunks` 设为 5。铁、铜、金门槛分别设为 1000000000、1、1，保证测试可触达预算上限。表中矿量单位为方块。

| 操作 | 预期结果 | 0.1.1 实测（铁 / 铜 / 金） |
| --- | --- | --- |
| 首次执行 `survey status`，再执行 `survey start` 与 `survey pause` | 从空记录开始，暂停后保持已提交测量 | 暂停时 2 个区块，137 / 145 / 58 |
| 正常停服、再启动，执行 `survey status` 和 `survey start` | 保留暂停状态和原进度 | 仍为 2 个区块，坐标、计数逐行相同 |
| `survey resume` 后读到 7 个已提交区块时，对临时服务器进程发送 SIGKILL | 重新打开 SQLite 时最后已提交的记录仍可读 | 7 个区块，516 / 659 / 187 |
| 用原世界与原数据库重启 | 运行中的任务自动继续，预算用完后停止 | 16 个区块，1210 / 1523 / 412。先前的 7 条明细保持一致 |
| 在预算上限执行 `survey resume` | 未调高预算时结果保持稳定 | 16 条明细与原摘要相同 |
| 停服把 `max-radius` 改为 3，启动后执行 `survey resume` | 新增 20 个区块 | 共 36 个，2759 / 3465 / 941。原 16 条均保留 |
| 对照服从首次暂停时的世界副本开始，用空账本将铁门槛设为 294 | 首圈实测 293，第二圈达标后停止 | 16 个区块，1210 / 1523 / 412。与上面故障恢复后的 16 条逐行相同 |
| 将出现 3 块偏差的 0.1.0 存档副本升级到 0.1.1，再执行 `survey resume` | 留存旧数据，按照当前存盘地形重测 | 旧表 36 行、铜 3468。新表 36 行、铜 3465。新表三项均与世界文件一致 |

独立核对在停服后读取 Anvil 区域文件，解码方块调色板和压缩索引，逐区块对比普通与深层矿石，同时核对 SQLite 汇总、游标和完整性。36 区块故障恢复存档、16 区块对照存档、36 区块旧版升级存档均通过。可在默认 zlib 区域压缩的 Paper 26.3 测试存档复验。

```sh
python -m pip install nbtlib==2.0.4
python tests/paper/verify_saved_ores.py /path/to/stopped/test-server
```
